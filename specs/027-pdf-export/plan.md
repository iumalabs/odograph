# Implementation Plan: Maintenance History PDF Export

**Branch**: `027-pdf-export` | **Date**: 2026-08-11 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/027-pdf-export/spec.md`

## Summary

Add a new, non-D1 `src/server/reports/` module that builds a PDF document (via `pdf-lib`, newly
confirmed workerd-compatible) from a vehicle's already-fetched, already-duplicate-filtered service
and fuel records — the exact same data `computeVehicleAggregates`/`computeVehicleExpenseBreakdown`
already read, via a new small repository helper that reuses the identical
`Promise.all([listServiceRecords, listFuelRecordsWithEconomy])` + D-005 filter shape. One new GET
route serves the generated bytes as a downloadable file, mirroring the existing attachment-download
route's `c.body()` pattern with an added `Content-Disposition` header. No new table, no stored
report — generated fresh on every request.

## Technical Context

**Language/Version**: TypeScript 5.9, Cloudflare Workers (`workerd`)

**Primary Dependencies**: `pdf-lib` (new) — pure JS, no native bindings, confirmed workerd-
compatible (research.md); programmatic PDF construction only, no HTML-to-PDF/headless-browser
dependency.

**Storage**: D1 — no new table. Reads via a new `getVehicleHistoryForReport(db, ctx, vehicleId)`
repository function, structurally identical to `computeVehicleExpenseBreakdown`'s existing
`Promise.all` + D-005 filter (specs/026), returning the filtered lists rather than aggregating
them.

**Testing**: Vitest via `@cloudflare/vitest-pool-workers` — the route-level integration tests
follow the existing `vehicle-aggregates.test.ts` pattern (real D1, `SELF.fetch`); the PDF-
generation module itself gets a focused unit test asserting on the returned bytes' basic PDF
validity (`%PDF-` magic header) and that the byte count changes meaningfully between a populated
and an empty vehicle — not a full PDF-content-parsing test, which would need a second (parsing)
dependency this feature doesn't otherwise need.

**Target Platform**: Cloudflare Workers (`workerd`); client adds a single "Download report" button
wired to the existing vehicle-detail view, no new panel/state beyond triggering a browser download.

**Project Type**: Web application (existing single-Worker structure) — touches
`src/server/db/repository.ts` (new small read helper), a new `src/server/reports/` module,
`src/server/routes/v1/vehicles.ts`, `deno.json` (new dependency), and a small `src/client/`
addition.

**Performance Goals**: No new target — PDF generation happens in-memory, well within Workers'
memory/CPU limits for the report sizes this app produces (research.md: pdf-lib holds the whole
document in memory, fine for tens of pages).

**Constraints**: Repository layer remains the only D1 access point (Principle I) — PDF generation
itself lives in a separate, non-D1 module (`src/server/reports/`), mirroring how
`src/server/attachments/` already keeps R2-specific logic out of `repository.ts`; every field
missing from a record is rendered as "not provided," never fabricated (Principle IV, FR-007);
cross-tenant access refused identically to a nonexistent vehicle (Principle I); the new dependency
is declared via Deno's `npm:` specifier convention in `deno.json`, consistent with every existing
dependency (Principle X) — no Deno-runtime API used inside the Worker-side generation code itself.

**Scale/Scope**: One new npm dependency, one new repository helper, one new non-D1 module
(PDF generation — layout/pagination logic), one new route, a small client addition (one button, no
new state beyond triggering the browser's native download).

**Structure Decision**: New `src/server/reports/` directory, matching the established pattern of
giving each non-D1 concern (R2 in `attachments/`, email in `email/`, push in `push/`) its own
module rather than folding it into `repository.ts`. No new client component/panel — a report
download is a single action, not a data view, so it's a button wired into the existing
per-vehicle section rather than a new panel.
